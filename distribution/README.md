# Distribution files

This directory contains metadata used to package and publish PawPrints. For installation, see [INSTALL.md](../INSTALL.md).

| File | Purpose |
| --- | --- |
| `PawPrints.toml.in` | Borea content-index listing template: identity, release repository, license expression and compatibility bounds |
| `RELEASE-NOTES.md` | Player-facing release summary and limitations |

`python tools/build.py --stage` produces `dist/PawPrints-<version>-preview.zip`. The archive contains one `PawPrints/` directory, including `mod.toml`, the runtime libraries, part-support definitions, installation notes and licenses. User settings, logos and exported drawings live outside the installed mod.

The listing ID, install directory and runtime entry assembly are `PawPrints`. The listing template requires a real forum topic URL in place of `@AHWOO_TOPIC_URL@` before submission as `listings/PawPrints.toml` to the content index. The authored listing follows [RFC 0031](https://github.com/KSAModding/content-manager-design/blob/main/rfcs/0031-content-metadata-format.md); it is submitted to the index, not embedded in the mod archive. Release versions, download hashes and resolved install metadata are generated by the index tooling. The game and loader bounds reflect the supported build; they should change only after compatibility testing.

Package verification commands are in [DEVELOPMENT.md](../DEVELOPMENT.md#publication-checks). Listing requirements and validation commands are maintained in the [content-index contribution guide](https://github.com/KSAModding/content-index/blob/main/CONTRIBUTING.md). The [listing builder](https://ksamodding.github.io/content-index/) is an optional editor for that metadata.

## One-time GitHub setup

1. In PawPrints **Settings > Advanced Security**, find **Private vulnerability reporting** and select **Enable**. Verify that **Security > Advisories** offers **Report a vulnerability**. The policy links to that route; enabling it does not make submitted reports public.
2. Commit the reviewed `.github/workflows/checks.yml` with the source changes. Its **Checks / Portable checks** job runs automatically on `main` and pull requests. Wait for its first successful run in **Actions** before making it required.
3. In **Settings > Branches > Add classic branch protection rule**, use branch pattern `main`. Enable **Require a pull request before merging** and **Require status checks to pass before merging**; select **Portable checks** from the observed checks. Keep required approving reviews off for a solo-maintainer project. Keep force pushes and deletion disabled. No publishing token or game binary is needed for this workflow.
4. Use your GitHub noreply email for future commits if you want contact-address privacy. Changing Git configuration affects future commits only. The release audit reports existing contact-address exposure separately, without printing the addresses.

## Publish a Borea preview

1. **Finish the candidate.** Review and commit the intended source, run the portable checks, and build with `python tools/build.py --stage`. Run `python tools/repository_checks.py` and `python tools/release_audit.py`. If reviewing staged changes before committing, also run the documented `--staged` audit. Every runtime/UI change creates a new candidate; do not reuse an older candidate's native acceptance claim.
2. **Test that exact ZIP.** Run the extracted-package probe and critical manual/native checks on the supported KSA/StarMap versions. When KSA is closed, `python tools/acceptance.py --package dist/PawPrints-0.5.39-preview.zip` runs the isolated drawing scenario; it requires the documented local fixtures. Never launch it alongside another game. Start PawPrints in a real Borea instance too. Record the ZIP SHA-256 with `Get-FileHash dist/PawPrints-0.5.39-preview.zip -Algorithm SHA256`.
3. **Publish the GitHub preview.** From **Releases > Draft a new release**, choose the reviewed source commit and a matching tag, for example `v0.5.39-preview.1` for the first 0.5.39 preview. Use a new tag/version for later candidates. Attach the runtime `PawPrints-0.5.39-preview.zip`, copy the player-facing release notes and mark it **pre-release**. Publish only after the release checks pass. Do not attach private captures, logs, review documents or game files. Keep one ordinary runtime ZIP asset so the index can select it unambiguously; GitHub already supplies source archives.
4. **Verify the hosted artifact.** Download the ZIP from the published release into a separate folder. Its SHA-256 must equal the tested ZIP. Run the extracted-package probe against the downloaded copy. A local build or successful upload alone does not verify the download. Keep the tag, source commit, ZIP hash and acceptance results together in the local release record.
5. **Create the real forum topic.** Post in the appropriate Ahwoo KSA mod section. Include what PawPrints does, supported versions, preview limitations, installation instructions, source/release links and a screenshot you have rights to share. Copy the actual topic URL into `links.forums` in `PawPrints.toml.in`. Do not leave the placeholder or invent a URL.
6. **Submit the listing.** Use the [listing builder](https://ksamodding.github.io/content-index/) or fork [content-index](https://github.com/KSAModding/content-index). Add the completed template as `listings/PawPrints.toml`. Preserve `id = "PawPrints"`, the release repository, `MIT AND OFL-1.1`, Windows-only support and the tested game/loader bounds. Open the listing PR from `DymndLab` so repository ownership supplies the ordinary ownership proof. Follow the current contribution guide if using another account.
7. **Run index validation.** In the content-index checkout, install its `tools/requirements.txt` and run `check_layout.py`, `check_schema.py`, `check_index.py`, `check_license.py`, `check_status.py` and `check_images.py` from `tools/`. Also run `python tools/check_release.py listings/PawPrints.toml`; it needs a sibling content-index-releases checkout and network access. Use the current official instructions if tooling changes. Resolve validation failures rather than widening compatibility claims to make them pass.
8. **Verify delivery through Borea.** After the listing merges and the release is indexed, refresh Borea and allow the preview channel if necessary. Install in a disposable instance with the supported game/loader. Launch, generate and export a PNG, then verify reinstall/update/removal preserves profile settings, logos and exports. Test an actual update when a second release exists; a first-release reinstall does not prove upgrade compatibility. Record outstanding gates honestly.

After listing, the index watches new releases. Update metadata when compatibility, links or dependencies change. Keep each published version and artifact immutable; publish a corrected version instead of silently replacing a downloaded ZIP. The [official contribution guide](https://github.com/KSAModding/content-index/blob/main/CONTRIBUTING.md) is authoritative for current submission rules.
